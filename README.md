# Тестовое задание — управление картографическими слоями

React 19 + TypeScript + [vedro](https://www.npmjs.com/package/vedro). Vite как сборщик.

Слои: температура, ветер, инсоляция. Для каждого — включение/выключение,
регулировка прозрачности, статус `loading / success / error`, повторная
загрузка после ошибки; при включении слоя выполняется мок-запрос к API.

## Запуск

```bash
npm install
npm run dev      # разработка
npm run build    # прод-сборка + проверка типов (tsc -b)
```

## Структура проекта

```
src/
  types.ts                  доменные типы (LayerState, LayersState, LayerStatus)
  config/layers.ts          конфигурация слоёв (единственное место, где они перечислены)
  api/mockLayerApi.ts       мок запроса к бэкенду: задержка, случайная ошибка, AbortSignal
  store/layersStore.ts      единственная точка создания vedro-стора
  hooks/useLayer.ts         подписка компонента на один слой (по ключу)
  hooks/useLayerActions.ts  вся бизнес-логика: toggle / opacity / load / retry
  components/
    LayerControlPanel.tsx   список слоёв
    LayerItem.tsx           строка одного слоя (checkbox, opacity, статус, retry)
    LayersSummary.tsx       агрегированная сводка (пример стор-вайд селектора)
    StatusBadge.tsx         презентационный компонент статуса
  App.tsx                   сборка начального состояния и Provider
```

Разделение ответственности:

- **UI-компоненты** не знают про API и внутреннее устройство стора — только
  рендерят данные из хуков и вызывают обработчики.
- **Состояние** нормализовано как словарь `Record<layerId, LayerState>`, а не
  массив: обновление одного слоя — точечная запись по ключу.
- **Бизнес-логика** (`useLayerActions`) отделена от UI и от способа чтения
  состояния (`useLayer`).
- **API-слой** (`mockLayerApi`) изолирован и заменяется на реальный
  fetch/GIS-сервис без изменений в компонентах.

## Управление состоянием в vedro

`vedro` создаёт единственный инстанс стора (`createVedro` → `<Provider>`,
внутри `new Vedro(state)` в `useRef`) и даёт `useSelector`, `useStore`
(доступ к `dispatch` / `get` / `on` инстанса) и `Provider`.

Я прочитал исходники пакета, чтобы понять, как именно уведомляются
подписчики:

- `useSelector` слушает общее событие `"@state"` (срабатывает при любом
  dispatch), пересчитывает селектор и сравнивает результат через
  `JSON.stringify` — перерисовка только если значение изменилось.
- `dispatch(key, value)` / `on(key, cb)` — точечный путь: уведомляются только
  подписчики конкретного ключа.

Поэтому:

- **`LayerItem`** подписан на свой слой через хук `useLayer`
  (`store.on(layerId, cb)`), а не через `useSelector`: изменение одного слоя
  не приводит к пересчёту селекторов и перерисовке остальных строк.
- **`LayersSummary`** использует `useSelector`: агрегат по всему стору
  нельзя получить подпиской на один ключ, а перерисовывается только сама
  сводка.

## Асинхронность и race conditions

При быстром вкл/выкл/вкл или повторных retry ответ на **устаревший** запрос
может прийти позже актуального и перезаписать состояние. Защита в
`useLayerActions` двухуровневая:

1. **`AbortController`** на слой — предыдущий запрос реально отменяется,
   мок-API уважает `signal` и отклоняется с `AbortError`.
2. **Счётчик последовательности** (`useRef<Map<layerId, number>>`, вне
   React-состояния, поэтому не вызывает рендер) — результат применяется, только
   если запрос всё ещё самый свежий для этого слоя.

Каждое обновление стора читает свежее состояние через `store.get(layerId)` в
момент завершения промиса, а не из замыкания рендера — параллельные изменения
(например, opacity, пока слой грузится) не теряются.

`StrictMode` оставлен включённым: двойной вызов эффектов в dev — бесплатный
стресс-тест на такие гонки.

## Строгая типизация

`any` в проекте нет, `tsconfig` со `noUnusedLocals` / `noUnusedParameters`.
Всё состояние типизировано через `Record<LayerId, LayerState>`.

## Отсутствие лишних render

- `LayerItem`, `LayerControlPanel`, `StatusBadge`, `LayersSummary` обёрнуты в
  `React.memo`, пропсы стабильны (`layerIds` — константа модуля).
- Строка перерисовывается только при изменении **своего** слоя (подписка по
  ключу).
- Служебные данные для отмены/гонок хранятся в `useRef`, а не в состоянии.

## Масштабирование с 5 до 100+ слоёв

- Новый слой добавляется одной записью в `config/layers.ts` — ни стор, ни
  логика, ни компоненты не меняются.
- Словарь по ключам даёт O(1) на чтение/запись слоя (вместо поиска по массиву).
- Стоимость одного изменения не зависит от числа слоёв: подписка по ключу
  уведомляет только одну строку.
- Состояние запросов изолировано по слоям (свой `AbortController` и счётчик на
  каждый `layerId`), поэтому параллельная загрузка десятков слоёв не создаёт
  конфликтов.
- Если список вырастет до сотен видимых строк, следующий шаг — виртуализация
  списка (например, `@tanstack/react-virtual`); архитектура состояния при этом
  не меняется.

## Использование AI

Использовал Claude:

- **Исследование незнакомой библиотеки.** `vedro` почти не встречается в
  публичном опыте, поэтому вместо догадок я прочитал его исходники
  (`node_modules/vedro/lib/**`): оттуда взято реальное поведение `useSelector`
  (`JSON.stringify`-сравнение на каждый dispatch) и подписки по ключу, на
  основе чего спроектирован `useLayer`.
- **Проектирование защиты от гонок.** Обсуждали варианты (только
  AbortController / только счётчик / оба вместе); выбрана комбинация, чтобы не
  зависеть от тайминга отмены.
- **Проверка результата.** `tsc` и `vite build` прогонялись после каждого
  шага (в истории коммитов каждый коммит собирается), это помогло сразу
  поймать несостыковки в типах vedro (`keyof S`, перегрузки `get`/`dispatch`).
- Код и README я вычитал и поправил вручную.
